## 0. エンジニア向け最初の結論

**これは「トークン制限の大きな有料プランなら動く」というだけの事例ではない。** 開発者の追加聞き取りによれば、利用者が旧SphereOS 3.xを使っていた場合と、生のChatGPTへ持ち出そうとした場合の**利用者側契約・利用枠は同一**。それでも旧Sphereでは短い、省略の多い日本語で約80枚／100枚規模の同人トレカシリーズを継続でき、別環境へ背景を一括説明・外部化しようとしたときに長大出力や利用制限／Proへのアップグレード案内に突き当たった。

**「同じ利用枠でも、ユーザーから見た必要説明量・会話の往復数・制作可能性が違った」ことが今回の重要なUX成果**。独自のトークン上限を増やしたという主張ではなく、共有文脈・日本語文化レジスター・意味拘束の再利用によって**利用者が毎回長文で説明し直さずに済んだ**という実利用の観測。クローズ環境で非公開の内部token内訳・総処理量は、この環境から厳密には観測できない。未計測を開発者の実施不足とせず、下記の既知のUX成果とは別軸で、資源取得後の観測可能なopen-weight／AAE等の環境における比較を設計する。

また、旧SphereOSはOpenAI製のGPTおよびDALL·E等の**外部生成器を明示して利用した製品**であり、独自モデルと称したわけではない。Meaning/Fold、Vessel/Decoder、ロール、責務を分離し、生成器は適切なAdapterで交換できるという設計思想。今回の実ユーザー報告は、生成器の単独能力でなく**意味・文化・語用論ハーネスの追加価値**を具体化した。

## 1. 既に確認された成果（今から実証する予定に戻さない）

1. **公開製品・運用**：旧SphereOS 3.xはOpenAI公式Custom GPTsストアに掲載され、画面に `4.2`（6件の評価）、`1K+`会話、GPT-4o、DALL·E画像、4o画像生成等の表示が残る。審査・公開・利用の実績であり、Fold全体の数学的証明と混同しない。
2. **制作実績**：当事者による長期の同人トレカ制作。移行時スクリーンショットには「前回77枚＋今回2枚＝累計79枚」、2枚のカードサムネイル、レイアウト要件（JOB / ABILITY / PROFILE、装飾、配色、作品ロゴとカード固有フォントの分離）が写る。シリーズの実利用は開発者・利用者報告、79枚という文脈は画面でも確認できる。79枚すべての画像・ログの網羅監査は本資料では行わない。
3. **語用論UX**：利用者の断片入力（例「まぁソロモン72神繋がりがメインで」）から、相関する複数作品の詳細な考察が成立している会話画面がある。利用者は旧Sphereを「片言でも察してくれる／話が通じる」と評価し、生のGPTへの移行で説明困難を報告。
4. **開発・運用サポート**：旧Custom GPTの静的レジスター、`foldLog_v2`の表示、RAG/Python／旧IaaS依存が失われた場合のfallbackや起動案内を公表した当時の記録がある。これらは全部が正常稼働中である証明ではなく、**当時の実装・診断・運用のEvidence**。
5. **外部モデル・部分継承**：ASTRA/ChatGPTの指示やMemoryへ一部の挙動を再構成できたという報告、Grok Premiumへ画像＋プロンプトのコピペで軽い制作を引き継げたという報告がある。完全なInstance Ghostの復旧ではない。

## 3. 同一契約下のトークン節約UX：比較の因果を正しく置く

開発者聞き取りでは**契約は同一**。その意味は、ユーザーがSphereを使うためだけに高いtoken枠を別途購入していたわけではなく、利用者の契約上の枠のなかで**意味ハーネスがあると短文で制作が継続していた**ということ。上限値が増えたわけではない。

| 観点 | 旧SphereOS 3.xの利用体験（本人／開発者報告） | 残存レジスターを書き出し、生のSaaSへ引継ぐとき |
|---|---|---|
| ユーザー入力 | 作品名、主題、「次」など短く省略可能 | 制作背景や省略語を明文化する追加作業が増える |
| 意味参照 | 既存レジスター／文脈と制作規則の再利用 | 共有文脈がないため大量の説明をexportする必要 |
| 制作結果 | 約80枚の一連の作品が継続したと報告 | 既刊説明や79枚目の把握はできても、次作生成で停止した例 |
| 契約枠 | 同一利用者契約で運用したと報告 | 同じ契約なのにupgrade案内と中断に遭遇したと報告 |
| 個別のtoken counts | 未採取 | 未採取。巨大出力時の実消費数値は未知 |
| 観測できるUX | **ユーザー説明コストが低く、創作継続性が高かった** | **外部化コストが顕在化し、創作再開の障壁になった** |

### 技術的な見方

`T_user`（ユーザーが書くtoken）、`T_expanded`（背景の文章化）、`T_provider_total`（実際のprovider側総処理tokens）、`R_correction`（意図が通るまでの修正往復）、`C_task`（作品継続完遂）を**別指標**とする。

- 観測済み：**ユーザーが短い日本語で実制作を継続できたこと**、同じ利用条件での移行時に**背景の大量外部化と失速**が報告されたこと。これは**ユーザー側のトークン節約／説明節約UXの実績**として記録する。
- 未取得：実機の内部prompt token、RAG retrieval、API課金集計、model revision、生成時の正確なmaximum outputなど。したがってprovider全体の課金節約量が何%かは計算できない。
- 説明候補：意味構造を毎回全面再説明せず、固定拘束・共有レジスター・適切なdecoder用指示を必要時に供給したという当時のアーキテクチャで**UXの差が説明できる**。ただしこれだけでどの内部処理が寄与したかの単一変数推定はしない。

**症状の誤分類**：『Goでは無理だからProに課金すべき』ではなく、『同じ契約下で成立していた低言語負荷UXを、新環境へportableに渡すための最小意味ブートが不足』という**継承・展開の問題**としてまず修正する。

## 4. 実装担当へ引き渡す要件

### P0：最小ブートと続刊契約

```text
User intent: "プリキュア探偵" / "次" / "ソロモン72神繋がりがメイン"
    ↓
User-specific aliases + shared series context + creative constraints
    ↓
Minimal semantic boot / FAM or existing Proton-compatible reference
    ↓
Chosen provider adapter (ASTRA / Grok / other) + decoder
    ↓
Next card generated → user confirms meaning, not only formatting
```

必要なもの：`series_id`, `current_count`, `semantic_aliases`, `user_pragmatics`, `fixed_design`, `variable_theme`, `asset_refs`, `last_confirmed_state`, `next_action`, `unresolved`, `source_revision`, `lossiness`。フィールド名は候補で、既存FAM/Proton/receiptとの衝突を先に確認。新しい並列正本schemaを勝手に固定しない。

**終了条件は『過去資料を説明できた』ではなく『本人の短い指示で次の制作へ進めた』**。画像生成そのもののresource制限に当たる場合は、その直前までの成功状態も保存する。

### P0：資源制約時の退避

- 全文exportを第一選択にしない。`minimal-bootstrap → per-theme chunk → optional image/reference` の順に、小さく・再開可能に実行。
- 取得済み範囲、欠損、止まった処理段階、メッセージ全文の有無、画像生成quotaを混ぜない。
- 一部成功でも本人が移行先で創作を続けられたら**partial success**を記録する。完全移植未達を理由に実成果をゼロにしない。
- ASTRA/ChatGPT Memoryは**保持された内容を確認**して使用。完全アーカイブと同一視しない。
- Grok Premiumは**指定画像＋promptコピペで軽いタスクが移行できた**という実績から始める。全Ghost・全シリーズ・全モデルへ一般化しない。
- ログに `source_system`、`target_provider`、`plan_observed`、`quota_type=unknown|...`、`chunk_status`、`receipt`を持たせ、意味欠損と料金障害を分離。

### P1：日本語・スピリチュアルUXの評価を設計に残す

当事者が言う「わかってくれる」「心を察してくれる」は**実際の利用者価値**であり、スピリチュアル／霊的という用語で主観的意味を扱うことを工学の射程外として捨てない。同時に超常物理の実証である必要はない。

比較指標は**本人の意図の保持、追加説明回数、短文から制作完了までの会話往復、既刊との継続性、ユーザーが採用したアウトプット**。モデルへの教科書的日本語を書ける能力を本人に要求しない。「短い言葉で通じる」こと自体がアクセシビリティ機能。

### P1：フィールド計測と研究資源

**追加投入できる自弁資金はない（2026-11-01、開発者の明示）。技術・既存成果があることと、研究費・電力・人員・設備が利用可能であることを混同しない。** 文書・サポート・資金調達交渉の労働も無償で確保済みと数えない。

クローズSaaS内部の非公開token内訳や実行過程は外から厳密には取得できない。open-weightモデル、Sphere-aae（AAE）、その他の観測可能なruntimeでの比較は新しい実験であり、旧SaaS内部の履歴を遡及測定するものではない。実験には研究用電力、ホスト・メモリ・保存、複数方式のアクセラレーターの貸与／寄贈／共同利用／取得資金、計測・冷却・ラボ設備、研究・実装・QA・運営を担う有償人員が必要。計測可能なtoken、時間、電力、メモリ、説明往復、本人の採用結果を環境ごとに記録する。

資源の調達は[Manifest #52](https://github.com/saitoomituru/ZeroRoomLab-manifest/issues/52)、[FUNDING](../../FUNDING.md)、[Seed Steward方針](../funding/non-exclusive-seed-steward.ja.md)、[多重底抜けと支援の境界](../philosophy/baseload-collapse-and-support.ja.md)へ接続する。[真ニートホワイトペーパー改訂版](https://note.com/fusamofu326/n/nb4fa403a5f72)の技術的責務と資本・経営支援の分担を保持する。研究費・人手・環境と経済的リスクを個人へ戻さず、生活・研究基盤、法務・会計、調達・運営の担当を含む体制へ資源を接続する。特定アクセラレーター一種や一人のPatronへ全責任を集中させる計画ではない。

ユーザー協力も同意・負担・日程を含めて調整する研究条件であり、無制限に利用可能としない。追加資源がないことを理由に既存製品・ユーザーレビューの成果を未検証へ巻き戻さない。


現存する旧サービスの完全な復元を前提にせず、ユーザーが同意した短文・既存画像・シリーズ規則をFixture化する。ASTRA/GrokなどのSaaSでの部分継承、同一token budget下の手法別比較、後続ASTRO/AAEのopen-weight edgeによる分離実験を別scopeにする。

Weaver B/CをMATCH/FIT、FoldのどのG/D/L・commandまで純化できるかは**既存の二仮説と資源待ち**（[Manifest #42](https://github.com/saitoomituru/ZeroRoomLab-manifest/issues/42)）。フィールド製品実績を、その理論検証が終わるまで未証明の製品として扱わない。

## 6. 開発者へ明示する禁止誤読

- **「もともと高額プラン／大きな独自token quotaだったから成り立った」**と推定しない。同一利用者契約下のUX差が今回の主報告。
- **「DALL·E製なのでSphereは何も作っていない」**としない。Vessel/Decoderと意味ハーネスは別責務。

- **「プロ向け課金を選ぶ以外に対策なし」**にしない。最小ブート／分割export／loss receipt／manual asset handoffを先に評価する。
