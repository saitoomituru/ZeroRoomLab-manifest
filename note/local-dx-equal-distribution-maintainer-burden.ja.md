# 地元DXの「住民頭パーセント均一平等」が末端デベロッパーをニートにする問題

> Status: `[NOTE]` `[POSITION-TALK]` `[NON-CANONICAL]`
>
> 記録日: 2026-07-29
>
> 対象: 地域DX、町内会・自治体・観光AR等の小規模デジタル公共財を、少人数または個人の末端developerが実装・保守する場合の負担構造

## 1. 苦言

地域DXで「住民一人あたり同じ割合で利益を配る」「全住民へ均一にサービスを届ける」ことだけを平等の尺度にすると、開発・保守・実地調整を引き受ける少数者の投入時間、専門技能、機材、更新責任、赤字リスクが勘定から落ちる。

その結果、住民側では一人あたり小さな便益として薄く分配される一方、末端developerには開発費、SDK追従、OS更新、ストア対応、3D／AR asset保守、現地調整、問い合わせ、機材費等が集中することがある。

これは「住民平等」そのものへの反対ではない。**便益の均一配分と、生産・保守負担の均一性は別の変数である**という指摘である。

```text
住民N人
  ↓
便益を広く薄く分配

しかし

実装者1〜数人
  ↑
開発 + 保守 + 現地対応 + vendor追従 + 機材 + 赤字リスク
```

利用者頭数だけを分母にして公共性を評価すると、供給側の極端な負担集中が見えなくなる。最悪の場合、「地域のためにDXを作った人ほど、そのDXを維持するための無償・赤字労働で通常の就労可能性を失う」という逆転が起きる。本noteではこの状態を挑発的に「末端デベロッパーをニートにする」と呼ぶ。

## 2. 高畠AR系から得た設計上の教訓

高畠AR+のような地域ARは、ARそのものだけで完結しない。アプリ、character asset、3D／AR asset、実地コンテンツ、OS／SDK、配布経路、現地情報の更新が一つの運用鎖になる。

一度作れば地域に永久設置できる看板とは異なり、softwareはvendor、OS、store、device、SDKの変更によって保守作業が再発する。利用人口が小さい地域ほど、この固定的な追従費を利用者数で回収しにくい。

したがって次世代の地域DXでは、地域ごとにruntimeを抱えるのではなく、可能な範囲で次のように分離する。

```text
共通runtime / open interchange format
        +
地域World data
        +
地域固有asset
        +
交換可能なrenderer / AR adapter
```

特定vendorや一つの行政事業が終了しても、地域側の3D、World、character、位置情報等まで一緒に失わない構造を優先する。

## 3. 平等の定規を一つにしない

地域DXを評価するとき、少なくとも次の定規を分離する。

- **Access equity**: 住民が利用できるか
- **Benefit distribution**: 便益が誰へ届くか
- **Production burden**: 誰が何時間・何技能を投入したか
- **Maintenance burden**: 更新責任が誰へ集中しているか
- **Capital burden**: device、server、developer account、現地機材等を誰が負担したか
- **Failure liability**: vendor終了や制度変更時の復旧を誰が背負うか
- **Asset survivability**: 予算やprovider終了後も地域assetを別runtimeへ移せるか

住民頭数で均等化できるのは、このうち一部だけである。

## 4. Position-talk boundary

このnoteは、自治体、町内会、国、特定企業を一律に敵と定義するものではない。また、個別案件について違法性、契約違反、不当利得等を認定する文書でもない。

一方で、「公共目的だから末端実装者の赤字は善意で吸収されるべき」「利用者全員に均等な便益があるから負担構造も公平である」という推論も採用しない。

公共性を維持したいなら、実装者の持続可能性も公共インフラの一部として測定する必要がある。

## 5. SphereASTRO / Atlantis側への設計入力

この問題への技術的回答は、地域ごとの専用アプリを無限に抱えることではない。

SphereASTRO等では、VRM／GLB等の交換可能asset、World data、renderer adapter、AR adapter、resource-aware presentationを分離し、一つの地域案件で作った基盤を他Worldでも再利用できる方向を試す。

地域固有の費用を「共通engineを一から作る費用」から「その地域のWorldとassetを維持する費用」へ縮退できるなら、末端developerへ集中する赤字火力を下げられる可能性がある。

これは現時点では設計仮説であり、自治体DX一般への実証済み解ではない。今後の実装、保守時間、移植性、実地運用receiptで検証する。
