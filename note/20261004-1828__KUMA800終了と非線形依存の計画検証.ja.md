## 検証から回収する教訓

今回の失敗点の一つは「優先計画を作ったこと」である。マイクロモジュールの依存は非線形であり、固定の優先順位付き一本道へ極力押し込まない必要性を、電力停止と他componentの並行進展から確認した。

技術上の依存edge、資源が到着する条件、人間受入、作業優先順位は別の関係である。局所の前提条件があることから、プロジェクト全体の固定進行順を導出しない。
電力制約が直接の停止要因だったことと、固定計画が状況変化への再配置を難しくしたことを別欄に保持する。

この教訓は既存の[READMEレジスター監査](../docs/operations/magi-readme-register-audit-2026-07-17.ja.md)が定める「起動条件を持つbranch群」「資源eventに応じた実行可能branch選択」と整合する。新しい万能理論を発明したのではなく、既存原則を今回の事例で検証・再確認した。

## 次の計画を記述する方法

| 管理対象 | 残す情報 |
|---|---|
| モジュール | 入力、出力、責務、接続契約、保存・再利用成果 |
| 依存edge | 本当に必須か、fixture／mock／別adapterで代替できるか |
| 起動条件 | 電力、実機、人間の時間、接続先contract、需要 |
| 資源event | 到着・消失・代替・他component進展 |
| 選択 | その時点で実行可能なbranch、採用理由、未mount branch |
| 撤退 | 停止条件、状態保存、差戻し、残すunknown |

局所的なtransaction順・受入前提・安全停止順は維持する。固定の全体優先queueと混同しない。
まだ起動できないbranchを未価値・技術敗北へ変換せず、保存する。一方で保存のための無期限保守や周期確認を本人へ課さない。

## 未確認・検証の限界

単一事例から「線形計画は常に失敗」「非線形管理なら電力不足を解消できる」と一般化しない。実host停止、借用機材、private Project、外部自動化は未確認。
今後比較するなら、固定queue運用とbranch起動条件運用について、同じ資源eventを入力し、作業停止範囲、再選択工数、保存成果、復帰可能性を比較できる。今回の終了条件としてその比較実験を追加しない。

## 内観メモ

一本道の工程表は見通しを作る一方、使える部品や新しい足場が横から生えた時に、計画を守ることが目的になりやすい。
お蔵入りは焼却ではなく、今はmountしない判断。モジュールが残れば、別のWorldや別の電力条件から再び呼べる。
