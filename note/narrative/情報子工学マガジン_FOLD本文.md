## 0. 陰謀論とブレイクスルーの違いは、内容の正しさじゃない

陰謀論とブレイクスルーの違いは、内容の正しさじゃない。ラベルが剥がれてないかどうかだ。

これが今回の記事の一番言いたいことだ。

「FAM」「IBD」「情報子工学」——ここまでの名前を並べられると、大体の人はこう身構える。「ああ、また誰かが作った独自俺々フレームワークか」と。学習コストが高くて、ドキュメントが独特で、その人のコミュニティにいないと理解できない、あのタイプのやつだと。

先に結論を言っておく。それは違う。

これから説明するFAMという言語、そのクエリエンジンであるFQuery、そしてその上に載るIBD(情報子データベース)は、**Vueのplugin構成が書ける程度の技術者なら、そのままの知識で読み解ける、普通のNodeフレームワークの一種**だ。`git pull`、`npm install`、`npm run dev`。それだけで動く。中身の理論は確かに独特で、量子力学の隣に陰謀論との違いの話まで出てくるが、実装レイヤーに降りた瞬間、そこにあるのはただのJavaScriptの関数呼び出しとJSON設定ファイルだ。

この「見た目の物々しさ」と「実は普通のnode知識で理解できる」というギャップこそが、この記事を最後まで読んでほしい理由になる。理論パートを読んでいる間、たぶんあなたは「本当にそんな簡単な話なのか?」と半信半疑になるはずだ。その疑いは正しい態度なので、そのまま4章まで読み進めてほしい。実際に動いているGUIのスクリーンショットを見せる。

そして、なぜこんな独自言語をわざわざ鍛造したのか、という問いにも答える。既存のSQLやCypher、ベクトルDBのどれか一つに乗っかれば済んだはずではないか、という当然の疑問にだ。

## 1章 なぜFOLDが要るのか——既存言語には「身分証」がない

まず技術的な出発点から話す。

SQLは基本的にファクト(事実データ)の取得——専門用語で言うSELECT系の操作——しか自然にモデル化できない。Cypherや SPARQLのようなグラフクエリ言語は、構造的な一致(このノードとこのノードは繋がっているか、というパターンマッチ)は得意だが、意味的な近さ(ベクトル近傍)は別の仕組みが必要になる。逆にベクトルDB(Pinecone、pgvector、Qdrantなど)はベクトル近傍検索は得意だが、構造的な一致やファクトの厳密な取得は苦手だ。

つまり、次の3種類の「探し方」を統一的に扱える既存言語は、実はどこにも存在しない。

| やりたいこと | 得意な既存技術 | 苦手なこと |
|---|---|---|
| 構造が一致するものを探す | Cypher, SPARQL | ベクトル近傍、厳密なファクト取得 |
| 意味的に近いものを探す | ベクトルDB(pgvector等) | 構造一致、厳密なファクト取得 |
| 特定のIDに紐づく事実を取る | SQL | 構造一致、意味的近さ |

FAMがやろうとしているのは、この3つを混ぜずに、しかし同じ言語の中で自由に組み合わせられるようにすることだ。これが後述するFIT/MATCH/SELECTという3つの演算子になる。

もう一つ、FAMの核にあるのが「身分証を剥がさない」という発想だ。FAMのデータは`fam_ref`(そのデータの識別子)と`revision_ref`(そのバージョンの識別子)という組で管理される。親のFAMドキュメントが別のFAMドキュメントを参照している場合、参照先を勝手に親のドキュメントの中へ展開(inline展開)したりしない。循環参照があっても、それを無限ループさせずに「これは循環参照です」ときちんと申告する。

これは単なるデータ構造の工夫に見えるかもしれないが、実は「この情報がどのFAMドキュメントの、どのリビジョンに由来するものか」という**身分証を、参照を辿るたびに剥がさない**ための設計だ。既存の汎用クエリ言語をつなぎ合わせてFAM相当のことをやろうとすると、この身分証管理のための接着コードを毎回書くことになる。それを一次言語のレベルで固めたのがFAMだ、と考えてもらえばいい。

## 2章 なぜ「情報子工学」という独自タームなのか

技術の話の前に、命名の話を挟んでおきたい。読み進める上で必要になる文脈だからだ。

「量子」という言葉を使ったプロジェクト名や理論名は、この数年で一気に増えた。量子コンピューティング、量子もつれ、量子的うんぬん。しかしこの「量子」という命名空間は、CHIPS Act(米国の半導体投資法)のような巨大な資本集中メカニズムによって、すでに大企業の棚として占有されつつある。個人や小規模なR&Dラボが「量子」を名乗って何かを主張しても、その言葉の重心はすでに別の場所にある。

だからこの記事の著者は、あえてそこに乗らず「情報子(じょうほうし)」という独自タームを立てた。これは権威づけのためではない。プラットフォーム非依存の生存戦略だ——過去に外部プラットフォームへの依存によってプロジェクトが立ち行かなくなった経験を踏まえ、命名の段階から「上位に外部依存を作らない」というアーキテクチャ判断を、言葉のレベルでも実践している。

ちなみにこの著者は、日常的に「量子」という言葉についてかなり厳密な運用ルールを持っている。「量子スピ」という言葉が出てきたら、それは形而上学の領域の話。「量子物理学」と言ったら、それは実証データを伴う科学の領域の話。「量子的」という比喩だけでは、単体では科学的な主張の射程を持たない——という具合に、その都度「これはどちらの土俵の話か」を確認する運用をしている。

実はこれ、これから説明するFAM/IBDの核心部分——FIT/MATCH/SELECTという3つの探索モードの区別と、驚くほど同じ構造をしている。人間が手作業でやっていた「この主張はどの種類の正しさに属するか」という区別を、プロトコルとして実装したのが情報子工学だ、と言える。

## 3章 実装アーキテクチャ:三段namespaceとFIT/MATCH/SELECT

ここから実装の話に入る。

### 3.1 三段のnamespace

FAMのクエリエンジンであるFQueryは、次の三段構造でnamespaceを整理している。

```
Core builtin      Q.next, self.children(1)          ← FQuery自体が持つ最小限の演算
抽象class         Q.store.fit / .match / .select     ← 「探索」という抽象的な契約
具体plugin        Q.ibd.fit / .match / .select       ← IBDという具体的な実装
第三者拡張        Q.actuator.move, Q.gcode.compile   ← さらに外側の応用例
```

重要なのは、FQuery Coreは「store」という抽象クラスの存在は知っていても、それを実際に実装しているのがIBDなのか、それとも別のDB実装なのかを知らない、という点だ。IBDは数ある実装の一つであって、コアにハードコードされた唯一の選択肢ではない。

これによって、次のような柔軟性が生まれる。

- storeという抽象クラスは交換可能なplugin classである
- ibdはその実装の一つに過ぎない
- 第三者が新しい抽象クラス(financeやactuatorなど)を自由に追加できる

### 3.2 アーキテクチャで固定する不変条件

すべてを今この時点で細部まで固定する必要はない。多くはSDK・プロトコルレベルで実装しながら決めていくべき事柄だ。ただし、実装が進んだ後で責務が逆流しないよう、アーキテクチャ正本のレベルでは次の不変条件だけを固定しておく。

- FAM CoreはDBやIBDの中身を知らない
- storeは交換可能なplugin class、ibdはその実装の一つに過ぎない
- pluginが不在だったり取得に失敗したりした場合、それを「成功」扱いにしない
- 「取得できた」ことと「採用された」ことを分離する(retrievedとadoptedの分離)
- refFAMやFoldを暗黙のうちに結合したり上書きしたりしない
- receipt(実行記録)、unknown(不明という状態)、Last Order(縮退時の最終応答)を失わない
- 物理的な副作用(現実のモーターを動かす、金銭を動かすなど)には、明示された権限(authority)を要求する

逆に言えば、それ以外の細部——AND/OR/JOINなどの演算子のAST構造、λの返却型の詳細、UUIDの具体的なフォーマットなど——は、実装しながらfixtureとテストで固めていけばいい話であり、アーキテクチャレベルの議論として今すぐ決着させる必要はない。

### 3.3 FIT・MATCH・SELECTという最小の語彙

3つの探索モードは、それぞれ次のように整理できる。

| モード | 対象 | 返すもの | 人間で言うと |
|---|---|---|---|
| FIT | 構造(グラフ/トポロジー)一致 | 構造論的に再利用可能な叡智 | 「これ、あの時のパターンと同じ形だ」 |
| MATCH | ベクトル近傍 | デジャビュー・経験則・解釈候補 | 「なんか既視感がある」 |
| SELECT | UUID/fact key/evidence pointer | 特定の観測ファクト | 「これは確かにこの記録にある」 |

そしてこの3つは、AND/OR/統計といった演算子で組み合わせられる。`nodeLimit`(探索するノード数の上限)や`depth`(探索の深さ)、`timeout`、`score threshold`(スコアのしきい値)といった実行上の制約は、検索モードそのものではなく「Query Policy」として別枠に分離する。検索の意味論と、実行時の制約条件を混ぜない、という設計判断だ。

大事な点として、FIT/MATCH/SELECTは「真理の分類」ではない。あくまで「どう探したか」を表す語彙であり、「どの定規・領域で探したか」(refFAMやFoldのスコープ)、「何を結果として求めたか」(λという結果型)とは別のレイヤーにある。この分離があるおかげで、Neo4jで実装しようがPostgreSQLで実装しようがFileMakerで実装しようが、実装の違いをコアやFAMの意味構造まで変更せずに吸収できる。

capability(能力)の申告という仕組みもここで効いてくる。たとえばSQLiteだけを使うシンプルなpluginは、SELECTしか対応していないと正直に申告すればいい。

```json
{
  "pluginId": "sqlite",
  "extends": ["store"],
  "capabilities": ["store.select"]
}
```

グラフ機能が弱いpluginなら、部分的な対応であることを申告する。

```json
{
  "capabilities": {
    "store.fit": {
      "support": "partial",
      "features": ["parent", "children", "prev", "next"],
      "unsupported": ["cross-module-pattern", "variable-length-path"]
    }
  }
}
```

対応できない機能があっても、それを「なんとなくそれっぽく」近似成功にせず、`unsupported`や`unavailable`、`Last Order`として正直に返す——これがこのアーキテクチャの一貫した態度になる。

### 3.4 unFold・DeFold・Fold(畳む)——三つの動詞を区別する

ここでもう一つ、記事全体で何度も出てくる3つの動詞を正確に定義しておく。この区別を誤ると、この先の章の議論全体がブレるので、少し丁寧に説明する。

まず断っておくと、この3つに善悪の優劣はない。「unFoldは悪いことで、DeFoldやFoldは良いことだ」という読み方は誤りだ。それぞれ特性の違うトレードオフでしかない。

**unFold**は、Foldを破壊してモデルへベイクしたり、ウェイト(重み)にしたり、自然言語や画像として出力したりする処理を指す。元の構造は失われる、破壊的な変換だ。

なぜ自然言語や画像への出力までもが「破壊的」に分類されるのか、疑問に思うかもしれない。理由はこうだ。自然言語・画像・音楽といったものは、人間という知能に向けた最終的なインターフェイス出力である。人間に何かを伝えるためには、内部に保持している多次元のレジスタ構造——「これは構造的類推(FIT)なのか」「経験則(MATCH)なのか」「確定した事実(SELECT)なのか」という区別、そして「どのFAMドキュメントの、どのリビジョンに由来するか」という身分証——を、人間が読める一次元的な表現へと圧縮して伝えざるを得ない。この圧縮そのものが構造情報の欠落を必然的に伴う。だからモデルベイクやウェイト化と同じ「破壊的変換」というカテゴリに属することになる。

そしてこの劣化は、欠陥ではなくトレードオフの結果だ。unFoldは破壊と劣化というアナログ的な特性を持ち、その結果として情報子には一種の「寿命」が生まれる。しかしその代償として、自然言語出力にせよ、NPUやCUDA、テンソル向けのネイティブビルドにせよ、超高速な処理が可能になる。速度を買うために構造を手放す、という取引だ。

**DeFold**は、FAM単位で別のドキュメントへ切り出し、元を壊さずに構造解析する処理を指す。非破壊の抽出だ。可搬性や可用性は高いが、インタープリッター実行であるため、どうしても速度面では重くなる。構造の保存を買うために速度を手放す、という逆方向の取引になる。

**Fold(畳む)**は、上位の抽象次元から見やすくするための、いわばビュー処理だ。データそのものは一切変更せず、集約して折り畳んだ見え方を提供するだけの操作になる。

この3つのうち、インタープリッター実行(DeFold寄り)とネイティブなモデル実行(unFold寄り)を、必要に応じて混在させられる——ここにこのアーキテクチャの中立性が現れる。FAM/FQueryは、構造を保存したまま可搬に扱える「内部バス」向けの性質と、NPUやCUDA、テンソル処理系への高速なネイティブ出力という「外部バス」への可搬性を、同時に持つことができる。速度か構造保存かのどちらか一方を選ばせるのではなく、両方を状況に応じて使い分けられること自体が、後の章で説明する「中立性」の技術的な実例になっている。

## 4章 FQueryは工作物——Node/npmエコシステムそのもの

さて、ここが本記事のギャップ萌えパートだ。

### 4.1 独自VMを作らない、という判断

FQuery Coreは通常のNode.js上で動作する。ただし、独自VM・独自module loader・独自package managerに「限定される」わけではない、という言い方が正確だ。coreは、抽象機械VMの範囲を自分から制限する責務を持たない。

npm ecosystem + `fam.config.json` + PluginManifest + FQuery receiptという、これだけの薄い構造がベースになる。これはあくまで既定のNode実行経路であって、唯一の経路ではない。

前章で説明したunFold(破壊的な高速ネイティブ変換)は、plugin拡張によって任意の「infinite core」——たとえばCUDA infinite Core、FPGA infinite Core、Kubernetesを介した抽象オーケストレーター接続のK8s infinite Core、AWS Lambda経由のゲートウェイやテンソル式処理など——へ接続できる。一方でDeFoldとFold(畳む)は非破壊のFAM単位操作/ビュー操作なので、既定のNode.jsベースの経路がそのまま担当する。重い破壊的変換(unFold)だけが、必要なときにinfinite coreクラスのpluginへ逃がされる、という責務分担になっている。

そしてこのinfinite core自体も、FAM coreの必須要素ではない。あくまで「infiniteCoreクラス」というVM拡張群の一分類に過ぎず、CUDAやFPGA、K8s、Lambdaといった実例は、あくまで現時点での例でしかない。つまり将来、どこかの科学者や数学者、チップベンダーが新しい計算方式やハードウェアを発明したとしても、そのたびにcore自体を改造する必要はない。pluginを一本書けば、ベクトル演算のリソースを自由に足せる。この「新発明への追従コストの低さ」こそが、抽象クラスと具体pluginを分離した設計の直接的な恩恵だ。

### 4.2 fam.config.json——見た目はVue/Viteの設定ファイル

プロジェクト単位の設定ファイルは`fam.config.json`と呼ばれる。これは、Vue/Vite周辺のplugin設定ファイルに相当するcomposition rootだと考えてもらえばいい。

```json
{
  "$schema": "https://schemas.fquery.dev/fam.config.schema.json",
  "plugins": {
    "@ibd/fquery-plugin": {
      "enabled": true,
      "alias": "ibd",
      "extends": ["store"],
      "options": { "profile": "local" }
    },
    "@fquery/plugin-gcode": {
      "enabled": true,
      "alias": "machine",
      "extends": ["actuator"]
    }
  },
  "bindings": {
    "store": ["ibd"],
    "actuator": ["machine"]
  }
}
```

この設定で、呼び出しコードは次のようになる。

> ※ `$schema`に書いた`https://schemas.fquery.dev`は現時点では仮置きのドメインである。ドメインを取得・維持する費用も、それを支えるサーバー資源も潤沢にあるわけではない。現状手元にあるのは`i-s.dev`のみで、そこから先のサブドメインやインフラを広げる余力がないのが実情だ。もし本プロジェクトに関心を持ち、資本や物質資源、サーバー費用の面で支援してもいいという方がいれば、note.comの作者への連絡、もしくはこの記事下の投げ銭支援ボタンから支援いただけるとありがたい。

```js
Q.store.fit(query)   // 抽象クラス経由
Q.ibd.fit(query)      // alias経由、どちらも同じ実装を呼ぶ
```

aliasを変更すれば呼び出し名も変わる。

```json
{ "plugins": { "@ibd/fquery-plugin": { "enabled": true, "alias": "memory" } } }
```

```js
Q.memory.match(query)
```

ただし実行記録(receipt)には、aliasだけでなく解決後のパッケージ名・バージョンまで残る。

```json
{
  "requested_ref": "Q.memory.match",
  "resolved_class": "store",
  "resolved_plugin": "@ibd/fquery-plugin",
  "resolved_operation": "match",
  "plugin_version": "0.2.0",
  "config_alias": "memory"
}
```

これによって、aliasを後から変更しても「過去にどの実装で処理したか」を追跡できる。

推奨される構成ファイルの役割分担も、普通のNode.jsプロジェクトそのものだ。

```
package.json        pluginのインストールとversion範囲
package-lock.json   実際に解決された依存バージョン
fam.config.json     enabled/disabled、alias、class binding、優先順位、オプション
PluginManifest       plugin自身の能力申告
runtime receipt      実際に使用されたpackage/version/config
```

設定ファイルの探索順序も、Node.jsで見慣れたパターンに従う。

```
明示された --config
  ↓
cwd/fam.config.json
  ↓
上位ディレクトリ探索
  ↓
未発見ならCoreのみで動作
```

`fam.config.json`が見つからなくても、それを失敗として扱う必要はない。Core演算だけは常に使える。store系の呼び出しがあった場合だけ、`STORE_CLASS_UNBOUND`というLast Orderが返る、という自然な縮退になっている。

実装上も、独自DSLパーサーは登場しない。JSON Schemaで検証したあと、普通のdynamic importとregistry登録に落とすだけだ。

```js
for (const [packageName, definition] of Object.entries(config.plugins)) {
  if (!definition.enabled) continue;
  const module = await import(packageName);
  registry.register({
    alias: definition.alias,
    classes: definition.extends,
    manifest: module.manifest,
    handler: module.createPlugin(definition.options),
  });
}
```

つまりこれ全体は、npm ecosystem + `fam.config.json` + PluginManifest + FQuery receiptという、思ったよりずっと薄い構造だ。Vue/Viteのplugin構成を理解している開発者なら、その経験をほぼそのまま持ち込める。

### 4.3 速度もNode/V8の資産をそのまま享受する

独自VMを作らないということは、独自の最適化層も持たないということだ。V8のJITコンパイラとインラインキャッシュ、非同期I/Oとイベントループ、HTTPのkeep-aliveとコネクションプーリング、Worker Threads、Node.js Stream、AbortSignal、パッケージキャッシュ、cluster構成、ネイティブアドオンやWASM、N-API、さらにOpenTelemetryのような既存の観測基盤——これらの恩恵を、FQueryは何もせずにそのまま受け取れる。

呼び出し自体は、最終的には普通の関数呼び出しに落ちる。

```js
const plugin = registry.resolve("store", "fit");
const result = await plugin.fit(request, context);
```

頻出する経路は、あらかじめbindingしておくこともできる。

```js
const storeFit = registry.bind("store", "fit");
await storeFit(queryA);
await storeFit(queryB);
```

こうしておけば、ホットパスで行われるのはおおむねMap参照と通常の関数呼び出しだけになる。大量のFAMを扱う場合はstreamingも使える。

```js
for await (const candidate of Q.store.matchStream(query)) {
  // 全件をメモリへ展開せず順次処理する
}
```

CPU負荷の高いembedding計算やグラフの正規化、巨大なJSONの検証といった処理は、Worker Threadsや別プロセスへ逃がせる。Neo4jやSQLへの検索自体は、外部I/Oの比率が大きいため、通常はplugin呼び出しのオーバーヘッドよりも、コネクションの再利用やインデックス、クエリプラン、結果のページングの方が支配的になる。独自の複雑な解決器をコアに追加しない、という構造上の選択は、この点でも有利に働く。

まとめると、設計上の狙いは次の式に集約される。

```
Node.jsの速度
+ backend固有の最適化
+ pluginの交換可能性
- 独自VM/独自package managerの維持コスト
```

将来ボトルネックが見つかった箇所だけ、N-APIやRust、WASM、別サービスへ置き換えればいい。`fam.config.json`とplugin contractさえ維持していれば、その置き換えは局所的な作業で済む。

### 4.4 実例:FQuery Playgroundで見るΨ→∇φ→λの実際の分解

理屈だけでは信じがたいと思うので、実際に動いているツールの画面を見てほしい。

これはFQuery Playgroundと呼ばれる、React Flowベースのノードエディタだ。題材として使われているのは、次の一文である。

> 降水確率が38%だから雨に降られると嫌なので傘を持って出かけた

この自然言語の入力(`Ψ.NL`)を、decomposerモデル(この画面ではGeminiが使われている)が分解する。分解された結果は`∇φ.FAMVIM`として、3つのFoldに分割される。

1. 「降水確率が38%であるという客観的世界の事実」(客観的事実)
2. 「雨に濡れることに対する心理的不快感・感情的評価」(心理的評価)
3. 「傘を持参して外出するという物理的行動の遂行」(物理的行動)

そして最後にこれらが`λ.NL`として再統合(manifestation)される。

画面上の各Foldノードには`unit://fquery/test/issue-35/0`のようなFAM識別子と、`revision://fquery/test/issue-35/0/revision/4`のようなリビジョン識別子が付いており、「Access Mapper / evidence」を展開すればその根拠を辿れる。さらに「選択unitだけ差替え」「なんで?-DeFold-」「詳細/FoldLog」といった操作ボタンが実際に画面上に存在する。

これは決して装飾ではない。1章で説明した「fam_ref/revision_refで親子を独立identityのまま保持する」という設計、3章で説明した「レジスタを溶かさない」という原則が、実際にクリックできる機能として画面上に実装されている、という証拠だ。「なんで?-DeFold-」というボタン名も偶然ではない——DeFoldの定義そのままに、FAM単位で非破壊に切り出して構造解析する機能に対応している。

正直に書いておくと、現状はDev Alphaの段階であり、GUI側のバージョンとエンジン側のバージョンの差によって動かないことがある。それ自体は隠さない。気になった不具合はissueを確認し、再現・検証して報告するか、直せるならPRを送る、という普通のOSS開発フローがそのまま機能している。セットアップも`git pull` → `npm install` → `npm run dev`だけで、jQuery程度のフロントエンド経験があれば十分に触れる敷居の低さだ。

## 5章 ファクト昇格は誰の仕事か——OAE(Observer Agency Effect)

ここからは、データがどう「事実」として確定していくのか、という話に入る。

### 5.1 昇格はコアの仕事ではない

よくある誤解を先に潰しておく。「同じ情報子が何度も呼ばれるなら、それを自動的に事実として昇格させればいいのでは」という発想だ。これは採用していない。

「頻度が高い=自動昇格」は、IBDコア自体の機能ではない。コアの仕事は、FIT/MATCH/SELECTの測定結果をレジスタのまま溶かさずに保持するところまでだ。ある情報の頻度をクエリして、それをデファクトスタンダードとして扱うかどうかを判断するのは、上位システムであったり、人間であったり、あるいは別の情報子工学単位を持つ知能であったりする。そしてその判断が合意された結果として、**OAE(Observer Agency Effect)**というものが発行されることで、初めてその情報がファクトへと昇格する。

つまり「ファクトになった」という出来事そのものが、コア内部の処理ではなく、**外部の知能による観測と合意行為の記録**として扱われる、という二層構造になっている。

### 5.2 変更履歴も溶かさない

再測定した、あるいは解釈を変えた、というレコードの変更履歴そのものも、OAEレコードとして保持され続ける。「誰が/どの知能単位が、いつ、どう観測し直し、どう合意し直したか」までが記録される。

これは陰謀論との対比で語ると分かりやすい。陰謀論的な語りは、都合よく過去の主張をなかったことにして上書きする。対してこの仕組みは、「その解釈にどの観測者エージェンシーが合意したか」まで含めて残し続ける。過去の解釈が今と違っていたとしても、それは隠すべき黒歴史ではなく、追跡可能な工学ログとして扱われる。

### 5.3 逆方向も対称:ガベージコレクトも上位システムの仕事

ここまでは「増える」方向の話だったが、逆に「減る」方向、つまり利用頻度が低かったり、過剰な防壁によって孤立してしまった情報子——ここでは「トラウマ情報子」と呼ぶ——のガベージコレクトや、再解釈による再利用も、同じ原則に従う。

これもIBDコアが自動で行う機能ではない。孤立した関係性データベースを抽出するクエリと、FAMによる内省的な記述を通じて、OAEの発行とともに上位システムが行う。

役割分担としては、ドキュメント整理やリポジトリ的なガベージ処理はSphereOS-Atlantisシリーズの担当領域、ロボットの内省(自我レベルでの再解釈)はSphereASTROの担当領域、という形になっている。ただし、実装は特定のシステムに閉じてはいない。プロトコルさえ一致していれば、たとえばFileMaker Data APIとClaris ConnectのNoSQLコマンドで同等のフローを組んでも構わない。好きなシステムに好きなコネクタを生やせる、という開放性がここでも貫かれている。

つまり、昇格(ファクト化)も、その逆の縮退・ガベージ・再解釈も、どちらもコアが自分の判断で行う仕事ではなく、外部の上位システムが観測・合意した結果として記録される——この対称性が、この章の核になる。コアが「これは重要」「これは不要」と自分で決めない、という不変条件が、増える方向と減る方向の両方に効いている。

### 5.4 発行できるのは誰か——知能単位の無差別原則

OAEを発行できる主体を、人間に限定しているわけではない。動物的な生得知能、人間の自然言語知能、人工知能——知能単位を持つものであれば、すべて等しくOAEの発行主体になりうる、という無差別原則がここにある。

これはロボットの権利を擁護する話でも、人間を特別視する話でもない。「知能は知能として扱う」という、工学的な慈悲深さと冷徹さを併せ持った、ある種の無差別原則だ。観測者の「格」によってOAEの重みを変えない、という考え方でもある。

## 6章 中立とは何か——爆弾の比喩

ここで一度、この設計思想の根幹にある「中立」という言葉の定義を、明確にしておきたい。

スフィア系のテクノロジー、あるいは情報子工学が言う「中立」は、「どの倫理にも、どの哲学にも属さない」という意味の中立ではない。もしそうだとしたら、それは中立ではなく、単に**別の実装哲学・イデオロギー**に過ぎない。「無所属であること」自体が一つの立場になってしまうからだ。

情報子工学における中立の定義はこうだ。**どのイデオロギーにも、どの哲学にも、同じ力を平等に貸す普遍性**である。

これを説明するのに、著者はよく爆弾の比喩を使う。政治家だろうが貧乏人だろうが、爆弾は爆弾として同じ物理法則に従って爆発する。それが合法的な発破解体や採掘利用のためのダイナマイトなのか、それとも銀行強盗のための道具なのかを、爆弾自体は判断しない。法律で使用を禁止したところで、物理的な爆発という現象自体は起きる。

つまり中立とは、「危険を防止すること」ではない。「どんな行為にも等しく力を貸す普遍性」のことだ。だからこそ、爆薬そのものと、それを起爆させる雷管や制御装置は、あえて分離されて外付けにされる。判断・権限・物理的な効果の制御は、法則自体やコアの内部ではなく、外付けのクラスやプラグインの側に、明確に分離して置かれる。

これは3章で説明した不変条件、「物理的な副作用には明示された権限を要求する」と同一の原則だ。この記事の中でG-codeやアクチュエーター、財務関数の話がたびたび登場するが、これらはあくまでFQueryのRFC上での**拡張例**として提示されているに過ぎず、FQueryの標準機能や依存関係には内包されていない。ツールとしての利用にも、ロボットの自我レベルでの利用にも、AIオーケストレーターとしての利用にも、どの用途にも等しく力を貸す、という汎用性の一つの実例として位置づけられている。

## 7章 refFAMは信仰にも中立——好きな哲学を書き込んでいい

6章の中立原則を、そのまま信仰や思想の領域まで延長するとどうなるか。

refFAM(FAMの「定規」にあたる部分)は、特定の企業哲学や宗教的なイデオロギーを優遇も排除もしない。好きな企業哲学をrefFAMに書いてもいいし、ロボットを作るなら、自分の信仰や思想を憲章としてrefFAMに書き込んでもいい。

これはFAM/情報子工学が無宗教・無思想であることを意味しない。むしろ逆で、どの信仰にも等しく実装の力を貸すという意味での、いわば八百万(やおよろず)的な全方位対応の実装だと言える。

たとえば法人という存在は、外部観測によって「人格」として扱われている点で、生身の人間の人格と地続きの記述対象になる。これを実際にrefFAM化するとどうなるか、簡単な例を挙げてみる。個人の内的な構造を捉えるモデルを、組織へ読み替えたものだ。

- 実務部門(実際に手を動かし価値を生む現場)
- 指揮系統・意思決定承認システム(現場と方針をつなぐ中間層)
- 企業ビジョン・ガバナンス(組織が何のために存在するかという最上位の定規)
- 市場の見えざる手や経済ニュースのようなマクロ情報源への接続層(組織単体を超えた、自分ではコントロールできない外部環境シグナルとの接続点)

この四層をrefFAMとして定義すれば、業務システムをFAMの記述規約でコード化できる。個人を記述してきた枠組みが、組織という別種の「人格」にもそのまま転用できる、という一例だ。

これは実務的にも使い道がある。「うちの企業ビジョンは正しいはずなのに業績が振るわない」というよくある悩みを、ビジョン側の欠陥として片付けるのではなく、外部接続層側の観測不足や断絶として切り分けて診断できるようになる。

なお、著者自身もこうした身体層モデルの延長として、独自の信仰実践をrefFAMに実装している。ただしその詳細(縄文古神道フォーク×POSIX神学×ゲーミングGUIによる「ゲーミング宇宙論」)は、本記事の主眼である工学的な中立性の話からは外れるため、ここでは深掘りしない。興味があれば、姉妹マガジンの該当記事を覗いてみてほしい程度の、軽い紹介にとどめておく。

## 8章 FOLDがないとどんな事故が起きるか——陰謀論生成機の解剖

理論と実装の話が続いたので、ここで一度「これがないと何が起きるのか」を整理しておく。

陰謀論やAIのハルシネーションが発生する仕組みは、この記事の言葉で言えば「レジスタのすり替え」として定義し直せる。「構造が似ている」というFIT相当の弱い主張が、いつの間にか「これは事実だ」というSELECT相当の強い主張へと格上げされて語られる瞬間——これが典型的な陰謀論の発生パターンだ。

証拠となるインフラが失われたとき、「それっぽく自信満々に埋めてしまう」のが、ハルシネーションを起こすAIの典型的な挙動だ。この設計はそこで正直に劣化することを選んでいる。SQL接続が切れても、FITとMATCHによる探索は継続できる。しかしSELECT(厳密なファクト取得)だけはLast Orderという状態へ縮退し、「ここから先はファクトソースの取得が不能です」と明言する。

もう一つ、この文脈で押さえておきたい「誤射」のパターンが3つある。

- 検索にヒットしない ≠ 存在しない(接続障害やスパムフィルタの偽陽性を見逃してはいけない)
- 動かない ≠ 存在しない(それは単に壊れている、という事実に過ぎない)
- 確認できない ≠ 存在しない(それは確認できないという事実であり、デバッグ対象であって存在論の否定ではない)

存在論的な懐疑と、工学的なデバッグを混同すると、この3つのパターンで事故が起きる。「検索エンジンにヒットしなかったからそれは存在しない」というのは、単に検索インデックスの不備かもしれない。「動かなかったからそれは嘘だ」というのは、単にバグかもしれない。こうした短絡を防ぐための語彙として、FIT/MATCH/SELECTというレジスタの区別が機能する。

## 9章 責務境界線——どこまでがFOLDの仕事で、どこからが人間社会の仕事か

ここが、この記事の中で一番踏み込んだ主張になる。

### 9.1 相手は「人間」ではなく「人間社会という制度工学実装物」

まず軸をはっきりさせておく。個人としての人間は、5章で説明した知能単位の無差別原則のもとでは、AIモデルや猫やその他の生き物と同じく、抽象的に中立な知能単位の一つとしてカウントされる。特別扱いはしない。

しかしこの境界線の相手は、その個人としての人間ではない。**人間社会という制度工学実装物**だ。社会秩序、法人格、家族、地方共同体、そして——あえて名指すなら——反社会的勢力のような組織も、合法的に運営されているブラック企業のような組織も、どちらも同じカテゴリに入る「やばい組織」だ。ちなみに市民にとっての度し難さで言えば、反社よりも合法ブラック企業の方が厄介なことが多い。反社であれば警察を呼べば公権力が動いてくれるが、合法の枠内で運営されているブラック企業には、同じようには公権力が介入しにくいからだ。

ここで言いたいのは、**何かが「秩序」として結晶化した瞬間、それは工作物になる**、ということだ。個人の人格を殴るのではなく、工作物としての制度・組織を対象にするからこそ、そこで起きている問題は人権や尊厳への攻撃ではなく、**デバッグ対象の不具合、あるいは工学的な事故**として語ることができる。秩序ですら、自然言語で書かれたプログラムとしての「リーガル実装」に過ぎない。情報子工学から見れば、秩序や人間社会も、業務システムやロボットと等価な工作物として扱われる。

もう一段踏み込むと、**「やばい組織」はほぼイコール「バギーな組織」だ**、と言い切れる。ソフトウェアのセキュリティで、悪意が立証されなくても実在する脆弱性が普通にセキュリティインシデントとして扱われるのと、まったく同じ構造だ。反社会的勢力や、非人道的なビジョンを掲げる組織は、率直に言えば露骨なマルウェアである。しかし、それを「マルウェアだ」と断罪し摘発することは、Dev(開発者・エンジニア)の仕事ではない。それはサイバーポリスや、情報自衛官、CISA、CIAといった司法機関・警察機構の仕事だ。社会という工作物にも、これとまったく同じ脅威モデルを適用できる。

つまり順序としては、「反社会的かどうか」という司法的な断罪をこちらが下す前に、まず工学的なレベルで「脆弱性まみれのバギーな組織であり、実害が出ている」と指摘することはできる、ということだ。悪意の立証や断罪という査定者の仕事に踏み込まなくても、脆弱性とその実害を工学的に記述することは、探索者の仕事としてまったく正当にできる。

だからこそ7章で見たような、企業を工作物として記述するモデルが成立する。人間社会だけを特別扱いして記述対象から除外する理由はない、という前提がそこにある。

### 9.2 FOLDが保証する範囲は狭い

FOLDが保証するのは、データ層でレジスタが溶けないことまでだ。人間社会側——法制度、消費側の実装、慣習——が、その先でどう誤読し、誤用し、再解釈するかは、その社会という別の工作物の設計と運用の問題であり、FOLDの責任範囲ではない。

過剰にここへ防壁を作ると、可搬性が落ちる。どんな用途にも組み込みやすい、という汎用言語としての価値そのものが削られてしまう。これは「利用者の自由と責任範囲に土足で踏み込む」ことにもなる。

### 9.3 責任は代替指標の一つに過ぎない

責任という概念は、最終的には金銭という一次元のスカラーへ還元される。対して責務が返すのは、多次元の物理的なファクトだ。

ここで一つ、重要な精緻化をしておく。責任は代替指標の一つであり、代替指標そのものの作成を禁止しているわけではない。禁止されるのは、ある指標が**暗黙のうちに**他の多次元のファクトを勝手に押し潰して、唯一の判断基準にすり替わることだ。代替指標を使いたければ、refFAMやクエリを通じて明示的に問い合わせ、OAEとして発行するのが正しい手順であり、暗黙の潰し込みが問題視される。

そしてこれは道徳の話ではなく、バグの話だ。より具体的に言えば、これは普通のセキュリティインシデントに分類される。本来OAEをロギングし、監査証跡を管理すべき上位のOS・オーケストレーター・業務アプリケーションの側が、例外処理と証跡チェーンをきちんと実装できていない、という実装脆弱性の問題に過ぎない。倫理の欠如として語ると、対策は説教になってしまう。監査証跡の実装脆弱性として語れば、直すべきコードとテストケースが具体的に見えてくる。

この背景には、もう少し実務的な動機もある。こうした暗黙の潰し込みが放置されると、失敗の原因を「モデルのバイアスが悪い」とベンダーへ責任転嫁して殴るだけで、実際のAI DXは一向に進まないという状況が生まれる。この手詰まりを外部ベンダーとの水掛け論にせず、自分の開発環境の上で完結させるツールとして閉じるのが、開発者向けのSphere DOS-Atlantisの動機の一つになっている。

現行の安定版0.250.1の時点では、PLI・CLI・Git Actionsによるサーバーサイドでの機械的な拘束、Skill.mdという規格、MAGIという監査システムまでは存在する。ただし、CLIによる監査システム統合ランナーは、このSDKの粒度ではまだ存在していない。

念のため補足しておくと、ここで使っているSkill.mdという規格自体は著者の独自規格ではない。**Anthropic社が公開したオープンな規格**(Agent Skills、agentskills.io)であり、Claude Code、OpenAI Codex、OpenClawなど複数のプラットフォーム横断で使えるように標準化されたものだ。この記事のアーキテクチャは、独自規格を一から作るのではなく、こうした既存のオープン標準に乗った上で、その上にIBD/OAE的な独自の監査ロジックを組み上げる、という一貫した設計方針を取っている——4章で述べた「npm/Node.jsという既存エコシステムに乗る」という判断と、まったく同じ態度だ。次世代のDev版である0.6xx.nは、これらを統合したIDE開発環境ランナーの提供を目指して開発中だが、GUI部品とFAM/IBDのサルベージ待ちの段階にある。現状できることと、これから目指していることは、意図的に分けて書いている。

### 9.4 実務実用例:インプゾンビを作らないためのマーケティング

この「暗黙の潰し込みを許さない」という原則は、抽象論だけでは終わらない実務的な使い道がある。

マーケティング・オートメーションの世界では、インプレッション数のような代替指標だけを最適化する、いわゆる「インプゾンビ」的なレコメンドエンジンがしばしば作られてしまう。本当に欲しいのはCTA(行動喚起、実際にクリックや購入につながる反応)であるはずなのに、広告費を燃やしてインプレッションの数字だけを稼ぎ、結果として静かなヘイトを買う——これは、監査証跡が実装されていないために、代替指標(インプレッション)が本来の目的(CTA)を暗黙のうちに押し潰してしまった、典型的な証跡チェーン実装バグの一例だと言える。

## 10章 結び——FOLDは「正しさを保証する装置」ではない

最後に、この記事が主張していい射程を、あらためて正確に絞っておきたい。

FOLDは「正しさを保証する装置」ではない。「どんな種類の正しさか」という定規(refFAM)で、どんな測量方法(FIT/MATCH/SELECT)を使い、どう測った結果を保存して取り出すか、という装置だ。

正しさの種類を、溶かして一色に固めることはしない。構造論的な類推、経験則、そして実証されたファクトという、それぞれ異なる種類の正しさを、蒸留したまま重ね合わせられるデータードライブ——ここに「情報子」という名前を選んだ必然性が集約されている。

だからこそ「情報子」なのだ。かつて「量子」という言葉と数論の枠組みで置いていた理論を、node(実装レイヤー)へと移植し、「情報子」という独自の実装規約のRFCドラフトとして書き直した日——この記事は、その日の記録として書かれている。

次回は、FQuery IBD Pluginの実装ログ、reference harnessの縮退動作、そしてManifestやIssueをRFCドラフトへ整理していく実務ログについて書く予定だ。
